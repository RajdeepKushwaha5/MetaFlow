1. Opening Hook: The Real Problem
=================================

Time: 0:00 to 0:35
Screen: MetaFlow UI, preferably the dashboard/home/About view.

What to say:

"Every data team already has alerts.

A pipeline breaks, a data quality test fails, a dashboard becomes wrong, and
the system creates another notification.

But the alert usually does not know the contract. It does not know lineage. It
does not know the owner. It does not know whether the column is sensitive. And
it cannot safely write the decision back to the metadata system.

That is the gap MetaFlow is built for.

OpenMetadata already knows the timeline of the data: assets, owners, lineage,
quality, changes, and governance. MetaFlow adds the AI action layer on top of
that timeline."

Show:
- MetaFlow is loaded.
- Sidebar/product surface is visible.

Judge takeaway:
- The problem is not "another chatbot."
- The problem is turning metadata context into governed next actions.

4. Flagship Flow: Contract Copilot
==================================

Time: 1:35 to 2:35
Screen: MetaFlow Contract Copilot.

What to do:
1. Go back to MetaFlow.
2. Open Contract Copilot.
3. Enter:
   sample_db_service.ecommerce_db.shopify.dim_customer
4. Click Generate Contract.
5. Show the generated YAML.
6. Click Publish.
7. Click Materialize tests.

What to say:

"Now I turn the OpenMetadata table into a governed data contract.

When I click Generate Contract, MetaFlow reads the live OpenMetadata asset and
builds a contract from the schema, profiler-style expectations, and lineage
context.

Notice that the contract is tied to the exact OpenMetadata FQN. It creates
expectations for customer_id, email, signup_date, loyalty_tier, and
email_consent_status.

It also creates operational gates: not-null, uniqueness, email format, enum
validation, and daily volume.

Now I publish it. This creates or reuses a native OpenMetadata data contract.

Now I materialize tests. Each quality gate becomes an OpenMetadata test case.
If the tests already exist, MetaFlow skips them instead of duplicating them.
For production, that idempotency matters."

Expected outcome:
- Generated contract appears.
- YAML includes:
  entity.fqn: sample_db_service.ecommerce_db.shopify.dim_customer
- Stats show:
  upstream sources: 2
  quality gates: 6
  schema expectations: 5
- Publish shows Published.
- Live status shows Draft.
- Materialize tests shows failed 0.
- skipped 6 is acceptable if tests already exist.

What to emphasize:
- This is native OpenMetadata contract/test work, not just a local YAML blob.
- Existing objects are reused safely.

6. Self-Healing Remediation Draft
=================================

Time: 3:05 to 3:35
Screen: MetaFlow Contract Copilot.

What to do:
1. In the violation box enter:
   Null rate on customer_id exceeded threshold (0.6% > 0.1%)
2. Click Draft remediation PR.

What to say:

"A contract is only useful if it helps during failure.

Here I simulate a real violation: the null rate on customer_id crossed the
threshold.

MetaFlow classifies the incident, drafts the likely SQL or dbt fix, identifies
files that probably need to change, and prepares a PR-style engineering
handoff.

This button does not blindly push code. It creates a reviewable remediation
draft. That is the right production posture: AI proposes, humans review, and
the metadata trail stays intact."

Expected outcome:
- Classification appears, usually null.
- SQL/dbt remediation diff appears.
- PR draft appears.
- PR title starts with:
  [Contract Heal]
- Labels include:
  contract-violation
  metaflow

Important note:
- This screen drafts a PR description. It does not create a real GitHub PR.
- GitHub issue dispatch is tested separately through Chat or Auto Remediation
  only if you intentionally want that side effect.
